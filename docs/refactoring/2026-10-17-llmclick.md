# LLMClick 리팩토링 변경 문서

## 1. 개요

- **날짜**: 2026-10-17
- **작성자**: ash-hun
- **대상 서비스**: LLMClick 저장소 전체. `core/`(실행 엔진, API, 공통 유틸), `modeling/`, `data/`, `evaluation/` 의 세 채널. 이번에 추가된 음성 레시피(`tts_piper`, `wakeword`, `data_speech`)가 프레임워크에 잘 편입되었는지 점검하는 것에서 시작해 전체로 넓혔다.
- **기준**: 기본 방안. 사용자 결정으로 조정했다.
  - config 하나로 모델을 만드는 기조와 `modeling/`, `data/`, `evaluation/` 작업 트리 구조는 그대로 둔다. 새 디렉토리를 만들지 않고 파일을 옮기지 않는다.
  - 앞으로 데이터, 평가, 모델링 세 방향으로 계속 확장하므로, 새 레시피가 그대로 가져다 쓸 공통 부품을 한 곳에 두는 것을 우선한다.
  - 모듈 docstring 은 프로젝트 규칙(한 줄), 테스트는 기존 구조(`tests/{core,modeling,data,evaluation}`)를 따른다.
- **기준 커밋**: `e3c12cc`
- **검증**:
  - pytest: 리팩토링 전 157 passed, 1 skipped. 리팩토링 후 164 passed, 1 skipped (기존 157 + 새 테스트 7). 테스트를 unit 과 integ 로 나누지 않았으므로 전체 실행 수치 하나로 적는다.
  - mypy (strict, 105개 파일): 전 0건, 후 0건. ruff: 전후 모두 통과. 문서 사이트 빌드 통과.
  - 새로 쓴 테스트: 7개 (`tests/core/test_files.py` 3, `tests/core/test_settings.py` 1, `tests/core/test_api.py` 1, `tests/modeling/tuning/test_units.py` 1, `tests/modeling/test_tts.py` 1)
  - fingerprint 동일성: 리팩토링 전 커밋과 후 코드로 같은 config 의 모든 stage fingerprint 를 계산해 비교했고 같았다(`llm_sft`, `evaluation_benchmark` 실험).
  - 실제 실험 재실행: `output/` 의 실험 15개를 각자의 `config.yaml` 로 다시 실행했다. 끝까지 통과했던 음성, LLM, 데이터 실험 11개는 모든 stage 가 캐시에서 끝났다. 나머지 넷은 리팩토링과 무관하게 다시 돌았다(비고).
  - 결과물 동일성: wakeword B6 를 빈 출력 폴더에서 새 코드로 처음부터 다시 학습해 `features.npz`, `jarvis.onnx`, `summary.json`, `wakeword.json` 과 검증 지표가 기존 결과물과 바이트 단위로 같았다.
- **요약**: 세 채널과 음성 레시피에 여러 벌로 손으로 쓰여 있던 같은 기능을 기능 이름을 가진 공통 부품 하나씩으로 모았다. 원자적 파일과 디렉토리 쓰기, JSONL 행 읽고 쓰기, 검증 행 나누기, 모델 로드와 해제, 레지스트리 이름 검사, config 의 로컬 경로 목록, 녹음 찾기, 프로세스 시작이다. 다른 레시피의 stage 모듈에 기대던 import 를 끊었고, API 의 모든 엔드포인트에 설명과 예시를 넣었다. 레시피 이름, config 키, stage 이름과 fingerprint, 출력 형식, API 경로와 응답 형태는 바뀌지 않았다.

## 2. 리팩토링 내용

### 공통 파일 쓰기와 행 파일 (`core/utils/files.py`, `data/rows.py`)

**리팩토링 전 (as-is)**

"임시 경로에 쓰고 끝나면 교체한다"는 절차가 저장소 안에 손으로 열네 번 쓰여 있었다. 파일 단위로 `modeling/tts/piper.py`(2), `modeling/wakeword/{features,detector,stages}.py`(3), `modeling/tts/stages.py`(1), `modeling/tuning/loop.py`(학습 재개 스냅샷), `evaluation/decision.py`(JevBench 내려받기), `data/rows.py`(2), `data/speech/select.py`, `core/utils/files.py` 의 `write_json` 이었고, 디렉토리 단위로 `FitStage`, `FitDetectorStage` 의 체크포인트 staging 이었다. 임시 이름 규칙도 제각각이었다.

JSONL 행 파일 읽고 쓰기는 두 벌이었고 동작이 달랐다. `modeling/tuning/stages.py` 의 `read_rows`/`write_rows` 는 쓰기가 원자적이지 않고 폴더를 만들지 않았으며, `data/rows.py` 의 것은 원자적이었다. 평가 채널과 음성 레시피는 tuning 의 stage 모듈에서 이 함수를 가져다 썼다.

**리팩토링 후 (to-be)**

`core/utils/files.py` 가 넷을 갖는다.

- `atomic_path(path)`: `path` 옆의 `<이름>.tmp` 를 내주고 블록이 끝나면 `path` 로 옮긴다. 블록이 실패하면 임시 파일을 지운다.
- `staged_directory(path)`: 빈 staging 디렉토리를 내주고 블록이 끝나면 `path` 로 이름을 바꾼다. 직전 크래시가 남긴 staging 은 먼저 비운다.
- `read_jsonl(path)`, `write_jsonl(path, rows)`: 빈 줄을 건너뛰고 읽는다. 쓰기는 원자적이다.

열네 곳 모두 이를 쓴다. `data/rows.py` 의 `read_rows`(없는 파일은 빈 목록), `write_rows`, `keep` 은 이름과 의미를 그대로 두고 내부만 위 함수를 쓴다. tuning 의 `read_rows`/`write_rows` 는 없앴고, 쓰던 곳(`modeling/{tuning,tts,wakeword}/stages.py`, `evaluation/{stages,decision,contamination,compare}.py`)은 `read_jsonl`/`write_jsonl` 을 쓴다.

**변경 이유**

멱등성은 이 프로젝트의 기본 보증이고 그 핵심이 원자적 쓰기다. 보증이 열네 곳에 흩어져 있으면 규칙을 바꿀 때(예: fsync 추가) 한 곳이 빠진다. 새 레시피는 이제 이 넷만 쓰면 된다.

### 검증 행 나누기 (`modeling/stages.py`)

**리팩토링 전 (as-is)**

`held_out_positions` 가 `modeling/tuning/stages.py`(LLM 과 임베딩 레시피의 stage 모듈)에 있었고, `modeling/tts/stages.py` 와 `modeling/wakeword/stages.py` 가 그 모듈에서 가져왔다.

**리팩토링 후 (to-be)**

모든 모델 레시피가 공유하는 `modeling/stages.py`(TrainStage, ValidateStage 가 있는 곳)로 옮겼다. 함수 본문은 같다.

**변경 이유**

모델 레시피라면 누구나 쓰는 함수가 특정 레시피 계열의 stage 모듈에 있으면, 새 모델 계열이 그 계열에 의존하게 된다.

### 모델 로드와 해제 (`modeling/tuning/backbone.py`)

**리팩토링 전 (as-is)**

`backbone.load(...)` 후 `try/finally: backbone.release()` 가 다섯 곳에 손으로 쓰여 있었다(`modeling/tuning/stages.py` 의 학습과 검증, `evaluation/{stages,decision,embedding}.py`).

**리팩토링 후 (to-be)**

`Backbone.loaded(device, checkpoint)` 컨텍스트가 로드하고 블록이 끝나면(실패해도) 해제한다. 다섯 곳 모두 `with backbone.loaded(...):` 를 쓴다. `data/teachers.py` 의 `Local` 은 여러 호출에 걸쳐 모델을 들고 있어야 하므로 그대로 `load` 와 `release` 를 쓴다.

**변경 이유**

가속기 메모리를 돌려주는 일은 모델 쪽의 책임이다. 새 평가 레시피나 학습 방법이 해제를 잊을 수 없게 한다.

### 레지스트리 이름 검사와 로컬 경로 목록 (`core/registry.py`, `modeling/config.py`)

**리팩토링 전 (as-is)**

"config 의 이름이 레지스트리에 등록되어 있는가"를 config 검증기마다 손으로 썼다. source(tuning, tts, wakeword, data), teacher, generator, reward(llm, data) 여덟 곳이다. API 가 접근을 제한할 로컬 경로를 모으는 `paths()` 의 같은 반복문도 여섯 곳에 있었다(`modeling/{tuning,tts,wakeword}/config.py`, `data/config.py` 2곳, `evaluation/config.py`).

**리팩토링 후 (to-be)**

- `Registry.check(*names)`: 등록되지 않은 이름이면 `ValueError("Unknown <kind> '<name>'; registered: [...]")`. 기존 메시지와 같은 문구다. 여덟 곳이 이를 쓴다.
- `local_paths(entries, keys=("path",))` 를 `Keyed` 옆(`modeling/config.py`)에 두었다. 여섯 `paths()` 가 이를 쓰고, 음성 레시피는 `keys=AUDIO_KEYS`(`path`, `audio_dir`)를 넘긴다.
- 음성 리팩토링 중에 만들었던 `check_registered` 는 `Registry.check` 로 대체해 없앴다.

**변경 이유**

레지스트리는 이 프레임워크의 확장 지점이다(새 source, teacher, reward, generator). 새 레지스트리와 새 config 가 같은 검사와 같은 오류를 한 줄로 얻게 한다.

### 녹음 찾기와 음성 레시피 (`modeling/tts/audio.py`, `modeling/tts/*`, `modeling/wakeword/*`, `data/speech/*`)

**리팩토링 전 (as-is)**

녹음 위치를 정하는 `audio_root`, 행의 파일을 찾는 `located` 가 `modeling/tts/stages.py` 에 있었고 `modeling/wakeword/stages.py` 가 이 stage 모듈을 import 했다. "소스를 읽고 오디오를 찾고 없으면 멈춘다" 반복문과 오디오 디렉토리 지문 계산이 `VoiceDataStage` 와 `ClipsStage` 에 따로 있었다. Whisper 를 만들고 `try/finally` 로 해제하는 코드가 `ListenStage` 와 `data/speech/verify.py` 에 따로 있었다.

**리팩토링 후 (to-be)**

- `modeling/tts/audio.py`(세 음성 레시피가 이미 함께 쓰던 오디오 모듈)가 `audio_root`, `located`(옛 위치 `modeling/tts/stages.py`), `recordings(source)`, `signatures(sources)`, `AUDIO_KEYS` 를 갖는다. 무엇이 빠지면 멈출지와 오류 문구는 각 stage 가 그대로 정한다.
- `Listener` 가 컨텍스트 매니저가 되었다. 청취 검사를 끈 `data_speech` 는 `nullcontext()` 로 같은 블록을 지난다.
- `FitStage`, `FitDetectorStage` 는 `staged_directory`, 나머지 파일 쓰기는 `atomic_path` 를 쓴다.
- wakeword 는 이제 다른 레시피의 stage 모듈을 import 하지 않는다. 음성 레시피끼리 공유하는 것은 `modeling.tts` 의 `audio`, `asr`, `piper` 세 모듈뿐이다.

**변경 이유**

한 레시피의 stage 를 고칠 때 다른 레시피가 깨지지 않게 한다. 새 디렉토리(`modeling/speech/`)로 분리하는 안은 작업 트리를 유지하라는 결정에 따라 하지 않았다.

### 프로세스 시작 (`core/settings.py`, `core/cli.py`, `core/api/app.py`, `core/config/experiment.py`)

**리팩토링 전 (as-is)**

CLI 와 API 서버가 각자 `.env` 를 읽고 `logging.basicConfig` 를 불렀고, 로그 포맷 문자열이 `core/config/experiment.py` 의 `LOG_FORMAT` 과 `core/api/app.py` 의 문자열 리터럴로 두 벌이었다.

**리팩토링 후 (to-be)**

`core/settings.py`(프로세스 수준 설정 모듈)에 `prepare_process()` 와 `LOG_FORMAT` 을 두었다. `.env` 를 환경으로 읽고 stderr 로 로그를 내도록 설정하며, 다시 불려도 핸들러가 늘지 않는다. CLI 는 `main()` 에서, API 는 라우터 import 전에 이를 부른다. `pipeline.log` 의 파일 핸들러도 같은 `LOG_FORMAT` 을 쓴다.

**변경 이유**

진입점이 늘어나도(예: 워커 프로세스, 노트북) 같은 준비를 한 줄로 하게 한다. 로깅 설정이 한 곳에만 있다(코드 규칙의 공통 logger 원칙을 기존 구조 안에서 적용).

### Local 선생 모델 (`data/teachers.py`)

**리팩토링 전 (as-is)**

`Local` 이 `identity()` 와 `load()` 에서 params 로 평가 채널의 모델 참조(`SourceExperiment`)를 똑같이 두 번 만들었다.

**리팩토링 후 (to-be)**

`source()` 메서드 하나가 만들고 둘이 이를 쓴다. 반환 타입은 타입 전용 import 로 `SourceExperiment` 를 적었다.

**변경 이유**

모델을 지정하는 params 규칙이 바뀔 때 한 곳만 고치면 되게 한다.

### API 문서 (`core/api/*`)

**리팩토링 전 (as-is)**

엔드포인트 10개 중 summary 가 있는 것은 1개(작업 취소)였고, 요청과 응답 예시는 없었다. `config_path`, 경로의 `job_id`, `experiment`, `Authorization` 헤더에 설명이 없었다.

**리팩토링 후 (to-be)**

모든 엔드포인트에 summary 와 필요한 경우 한두 문장의 description 을 넣었다. 모든 경로, 쿼리, 헤더 인자에 설명을 넣었고, `ConfigSummary`, `JobRequest`, `JobResponse`, `EvaluationSummary` 의 필드 설명과 예시를 넣었다. 예시 config 는 `configs/llm/sft.yaml` 과 같은 값이라 `/api/config/validate` 에 그대로 보내면 통과한다(테스트로 확인). 경로, 메서드, 인자 이름, 기본값, 응답 형태는 바꾸지 않았다.

**변경 이유**

API 는 config 를 받아 실행하는 공용 진입점이다. 레시피가 늘어도 호출자가 Swagger 만 보고 쓸 수 있게 한다.

### README 확장 가이드

`04. Extending` 에 "Building blocks a new recipe reuses" 표를 더했다. 원자적 쓰기, 행 파일, 항목별 캐시, 검증 행 나누기, 모델 로드, 레지스트리 검사, 로컬 경로, 녹음 찾기를 어떤 함수로 어디서 가져다 쓰는지 적었다. 새 데이터, 평가, 모델링 레시피가 같은 단계를 다시 쓰지 않게 하려는 것이다.

### 테스트

**리팩토링 전 (as-is)**

`tests/core`(실행 엔진, 레지스트리, API), `tests/modeling`(stage 템플릿, 각 레시피를 작은 모델로 끝까지), `tests/data`(가짜 선생 모델과 가짜 Piper, Whisper 로 데이터 레시피를 끝까지), `tests/evaluation`(평가 레시피를 끝까지). 대부분 레시피 하나를 끝까지 돌리고 결과, 캐시, 재개, 재실행 동일성을 단언하는 시나리오 테스트다. 각 파일의 첫 줄 docstring 이 보장하려는 요구사항을 적고 있고, 이 요구사항이 리팩토링의 기준선이었다.

**리팩토링 후 (to-be)**

기존 157개는 모두 남았고 단언은 바뀌지 않았다. 고친 것은 내부 인터페이스가 바뀐 데 따른 두 가지다. 가짜 Whisper(`tests/speech.py` 의 `FakeListener`)에 `with` 프로토콜을 더했고, `test_tts.py` 의 import 를 옮긴 함수의 새 위치로 바꿨다. 새 테스트 7개는 새 공통 부품마다 깨지면 실패하는 가장 작은 것이다.

- `atomic_path`, `staged_directory`, `read_jsonl`/`write_jsonl`
- `Backbone.loaded`(실패해도 해제)
- `prepare_process`(두 번 불러도 같은 상태)
- API(모든 경로에 summary 와 인자 설명, 예시 config 가 실제로 통과)
- 녹음 찾기와 `Registry.check`, `local_paths`

**변경 이유**

공통 부품은 여러 레시피가 기대므로 레시피 테스트와 별개로 자기 테스트를 가진다. 테스트 디렉토리 구조는 사용자 결정에 따라 기존대로 둔다.

### 공통 적용

손댄 파일의 모듈 docstring 은 프로젝트 규칙대로 한 줄을 유지했다. 새 함수와 메서드는 모두 타입 힌트를 갖고 mypy strict 를 통과한다(`data/teachers.py` 의 반환 타입은 순환을 피하려고 `TYPE_CHECKING` import 로 적었다). import 는 각 파일의 기존 정렬 방식을 따랐다.

## 3. 비고 및 특이사항

- **계획에서 바꾼 점**: 처음 계획한 `modeling/speech/` 공용 패키지 분리와 파일 이동은 작업 트리 유지 결정에 따라 하지 않았다. 소스 검사용으로 처음 만든 `check_registered` 는 저장소 전체를 보며 `Registry.check` 로 일반화해 없앴다.
- **코드 규칙과 프로젝트 규칙이 부딪힌 지점과 결정**: docstring 3~6줄 대 한 줄은 한 줄. 테스트 `unit/`/`integ/` 대 기존 구조는 기존 구조. api/service/repository 층 이름은 적용하지 않았다(기능 단위 모듈이 이 프로젝트의 규칙). 공통 logger 는 새 파일 대신 프로세스 설정 모듈의 `prepare_process` 로 적용했다.
- **일부러 남긴 것**:
  - `Backbone`, `DecisionHead` 의 추상 클래스(ABC): 모델 카탈로그 레지스트리의 기반이라 그대로 둔다.
  - 레지스트리 검사 중 문구가 다른 네 곳: architecture, evolve operators(목록), judge teacher, 평가 채널의 architecture. `Registry.check` 로 바꾸면 오류 문구가 바뀌어 그대로 둔다.
  - Stage 출력이 dict 인 것: 프레임워크의 JSON 직렬화 계약이다.
- **구조상 남은 의존** (고치려면 파일 이동이 필요해 기록만 한다):
  - `data/teachers.py` 의 `Local` 이 `evaluation.source.SourceExperiment` 에 기댄다(data → evaluation). 모델 참조 해석은 평가 전용이 아니라 모델 채널의 일이라, `modeling/` 쪽으로 옮기면 의존이 한 방향이 된다.
  - `modeling/llm/models/base.py` 와 `heads/` 가 서로를 함수 안에서 import 해 순환을 피한다.
  - `evaluation/{benchmark,decision,embedding,compare}.py` 가 `evaluation/stages.py` 의 `named`, `contamination` 을 쓴다. 채널 안의 공용 stage 모듈이라 허용 범위로 보았다.
- **작은 동작 차이**:
  - 원자적 쓰기가 실패하면 임시 파일이 남지 않는다. 임시 이름이 `<이름>.tmp` 로 통일되었다. 결과 파일, 캐시, fingerprint 에는 영향이 없다.
  - tuning 쪽 행 쓰기(`data` stage 의 `train.jsonl`, `validation.jsonl`, 평가의 `rows.jsonl`)가 이제 원자적이다.
  - tuning 쪽 행 읽기가 공백만 있는 줄을 건너뛴다. 전에는 JSON 오류였고, 이 저장소가 쓴 파일에는 그런 줄이 없다.
- **발견한 버그 (리팩토링 뒤 별도 커밋으로 수정)**: wakeword 의 증강과 스트림 테스트가 난수 시드를 녹음 파일의 절대 경로로 정한다(`modeling/wakeword/stages.py` 의 `rng_for(seed, row["audio"], ...)`). 같은 녹음이라도 폴더를 옮기면 다른 학습 창과 검증 잡음이 만들어진다. 그래서 `tests/modeling/test_wakeword.py` 의 첫 테스트가 pytest 임시 폴더 이름에 따라 가끔 실패한다(관찰: 여섯 번에 한 번, recall 0). 이번 리팩토링 중 간헐적 실패가 세 번 있었고, 이름을 기록한 한 번이 이 테스트였다. 나머지 두 번도 같은 원인으로 추정한다(미확인). 고치려면 시드 키를 파일 내용 해시나 소스 기준 상대 경로로 바꾸고 해당 stage 의 `version` 을 올려야 한다. 이미 만든 wakeword 실험의 결과가 달라지므로 동작 변경이다. 사용자 결정에 따라 리팩토링 커밋과 분리해 고쳤다. 시드 키를 파일 내용의 sha256 으로 바꾸고 `features` 와 `validate` stage 의 `version` 을 2로 올렸다. 같은 녹음을 다른 폴더에 둬도 학습 창과 검증 결과가 같은지 확인하는 테스트(`test_moved_recordings_make_the_same_windows`)를 더했다. 이 테스트는 수정 전 코드에서 실패하고 수정 후 통과한다. 수정 후 wakeword 테스트를 20번 반복해 실패 0번. 기존 wakeword 실험은 다시 실행하면 이 두 stage 부터 새로 계산되고, 수치가 조금 달라질 수 있다. 이미 내보낸 모델 파일은 그대로다.
- **리팩토링과 무관하게 다시 돈 실험**:
  - `jarvis-medium-ft-c77017d3`, `jarvis-wake-d4177b12`: 원래 검증에서 실패한 실험이라 validate 가 다시 돈다(실패한 stage 는 캐시하지 않음). wake 쪽은 같은 수치(0.0570)로 다시 실패했다. 음성 쪽은 저장된 config 에 `phrase_takes` 가 없어 기본값 3 으로 검증이 새로 돌았다(PR #22 의 기능).
  - `smoke-benchmarks-3c32208f`: 평가 stage 의 fingerprint 가 manifest 에 남은 값(10월 9일)과 달라 다시 돌았다. 리팩토링 전 커밋과 후 코드가 같은 fingerprint 를 계산하므로 원인은 그 사이의 실행 환경 변화(패키지 버전 등)로 보며 확인하지 않았다.
  - `sft-qwen3.5-0.8b-benchmarks-e7b8dffd`: 이전에도 완료된 stage 가 없던 실험이며, 이번에도 lm-evaluation-harness 실행 중 프로세스가 중단됐다(exit 134). 리팩토링한 경로(`Backbone.loaded`)를 지나지 않는 benchmark stage 다.
- **평가 채널의 기능 공백** (새 기능이라 하지 않음): `evaluation/source.py` 가 `TuningConfig` 만 받아 tts_piper 와 wakeword 체크포인트를 평가 채널로 다시 잴 수 없다. `evaluation_decision`, `evaluation_embedding` 과 같은 패턴의 `evaluation_wakeword` 레시피가 다음 후보다.
- **배포할 때 사람이 할 일**: 없음. 의존성, 설정 키, 출력 형식이 그대로이고 기존 `output/` 캐시도 그대로 쓰인다.
